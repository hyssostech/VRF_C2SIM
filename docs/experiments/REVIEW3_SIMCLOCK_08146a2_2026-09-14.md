## FINDINGS

### P1. MAJOR (NEW, introduced by this commit) - a +Infinity sim reading crashes the process, or manufactures an instant TASKABRT
`src/VrfC2SimApp/StallPolicy.cs:87` (`UsingSimClock ... simSeconds >= 0.0`),
`:257` (`if (ring is null || !double.IsFinite(clockNow)) return startClock;`),
`src/VrfC2SimApp/VrfC2SimService.cs:2783` (`if (usingSim && !simReadable) return;`),
`:2922` (`var oldest = ring[0];`).

MECHANISM. The F2 fix made `Admit` REFUSE a non-finite clock - correctly - but the caller's guard is
the same `>= 0.0` predicate, and `double.PositiveInfinity >= 0.0` is TRUE. So +Inf passes :2783,
becomes `clockNow`, and reaches `Admit`, which returns WITHOUT APPENDING. Two outcomes:

- **Empty ring** (the unit's first sample - `GetOrAdd` has just created it): line :2922 dereferences
  `ring[0]` on a zero-length list -> **IndexOutOfRangeException**. `MaybeCheckStalls()` is called
  bare from `TickLoop` (:556); only `_bridge.Tick()` and queued tick actions are wrapped
  (:545-551); `Program.cs` installs no `AppDomain.UnhandledException` handler. An unhandled
  exception on the `vrf-tick` thread **terminates the interface process**. Reproduced in the model:
  crash on the first check.
- **Non-empty ring**: `(clockNow - oldest.Clock) >= window` and `(clockNow - startClock) >= 60` are
  both trivially true against +Inf, so the gate opens on WHATEVER depth >= 4 happens to exist,
  however little sim time it spans. Measured on the RECAL doc's own tightest true negative (a
  0.23 m/s-of-sim crawler at 1.5x): +Inf arriving at wall 20/25/30/40/60/120 produces a TASKABRT on
  the SAME TICK, reporting 6.9 / 8.6 / 10.4 / 13.8 / 20.7 / 41.4 m "in the last 360 SIM s" on
  ~30-180 sim s of history. The identical feed with a finite clock never fires.

This is the F1 defect's shape again - a nominal window measured against a shorter real one - but
worse: it fires on the first tick, at any depth, and it has a crash branch. 1805ee3 did NOT have it
(it appended +Inf and corrupted the window instead).

REACHABILITY is unproven offline and is exactly the class of unknown the commit itself flags:
`VrfFacade::SimTimeSeconds` (VrfFacade.cpp:600-612) manufactures only -1.0 (null controller, zero
back ends, any exception) and passes `DtVrfRemoteController::simTime()` through unfiltered. -Inf is
harmless (it fails `>= 0.0` and reads as "no reading"); +Inf is not.

FIX (two lines, and it closes both branches):
```csharp
public static double SelectClock(bool preferSim, double simSeconds, double wallSeconds)
    => UsingSimClock(preferSim, simSeconds) ? simSeconds : wallSeconds;
public static bool UsingSimClock(bool preferSim, double simSeconds)
    => preferSim && double.IsFinite(simSeconds) && simSeconds >= 0.0;
```
plus, as defence in depth at the point of the crash, `if (ring.Count == 0) continue;` after the
`Admit` call at :2918 (or make `Admit` return a bool). A fail-first check exists for free: drive
`Admit` with +Inf on an empty ring and assert the caller can still read a sample; and assert
`!UsingSimClock(true, double.PositiveInfinity)`.

`src/VrfC2SimApp/StallPolicy.cs:298-301`, `VrfC2SimService.cs:2937`.

Measured first-verdict WALL times in sim mode on a frozen unit: 240 s at 1.5x, 60 s at 6.21x, 16 s at

### P7. NOTE - the dormancy line's volume and its quoted ceiling

### P9. NOTE - a jittering sim reading is diagnosed as `rollbackToSnapshot` and can suppress a true detection

## ADVERSARIAL REVIEW

**Competing hypothesis for P1, weighed and rejected: "`simTime()` can never return +Infinity, so the
finding is vacuous."** I cannot falsify it offline. But the finding does not depend on it. This
commit ADDED `!double.IsFinite(clockNow)` to `Admit` precisely because it could not rule out a
non-finite reading; so either that guard is dead code - in which case the fix bought nothing and
should say so - or it is live, in which case the caller lets exactly one non-finite value reach it
and the very next statement dereferences an empty list. The commit is internally inconsistent either
way, and the inconsistency is what I am reporting. Falsifier: the instrumented run the C16 doc
already owes for the TWO LIVE UNKNOWNS, logging `SimTimeSeconds()` every check - if it is always
finite, P1 downgrades to dead code that should be removed or documented as unreachable.

**Competing hypothesis for the wall-identity claim, weighed and rejected: "the model reproduces the
code's INTENT, not the code."** Guarded against by construction: before using the model on anything
new I made it reproduce, to the digit, four independent PRE-FIX numbers this commit's own comments
quote (1,195 entries / 171 NaN stamps / 8,955 s window; 1 warning and 84 suspended checks; 3 verdicts
with the first at wall 160 on 35.7 m; filled ring 49). A model that had drifted from the code would
not hit all four.

**Competing hypothesis for P4, weighed and rejected: "hysteresis already covers an unsteady
reader."** It covers a reader that flips faster than `ModeSwitchConfirmations`, which is what the
pass-1 finding-8 test drives and what my `A8` case confirms (mode holds, correct fire at 240). It
does not cover a reader that is out for three or more CONSECUTIVE checks, which is the deactivated-
back-end shape the commit itself argues is the realistic one. `A8b` is that shape and it produces
total, unannounced silence.

**Symptom still unexplained.** The oscillation sweep in P9 is non-monotonic in amplitude: 5 s and
200 s suppress the detection while 30 s, 100 s, 400 s and 1000 s do not. I traced this to the phase
relationship between the square wave, the 5 s cadence and the front prune rather than to a second
mechanism, but I did not characterise it fully, and I am recording it as an incompletely explained
observation rather than a footnote. It does not change P9's direction (the failure is real at two of
the six amplitudes tested); it does mean the boundary is not a clean threshold and a live jitter
measurement, not more modelling, is what would settle it.
