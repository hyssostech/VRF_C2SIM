## 9. Adversarial review

**Falsification gate on the one cause-shaped claim made here** - "the mesh branch was entered and
the mesh query returned nothing; the gate is not the failure":

  these objects.* Falsifier: nav-area rows naming the area, and gate successes. Checked: 259 rows
  name `NavArea-ground-platform MojaveCOA`, `MojaveAO20` appears 0 times, and
  `Node Is destination in nav area?: success` fires 101 times with 0 failures (6/0 for 1-35).
  REFUTED.
- Competing hypothesis B: *the "Planned nav path has not enough (0) points." rows belong to a
  different code path than the leg planning.* Falsifier: the row's position in the per-object
  sequence. Checked on M1A2 1: the nil row sits between the destination-in-nav-area success
  (wall 70.9) and the feature planner's "1 parts" (wall 72.1), on the same goal (ID=6) whose
  destination decodes to V1 exactly. REFUTED.
- Competing hypothesis C: *the mesh failed for a reason other than goal distance - e.g. the first

  Falsifier: successes and failures sorted by goal distance. Checked: the two populations do not

  sim 1,278, long after load. NOT REFUTED as a contributing factor for the 2 short failures, but
  it cannot explain the 110 long ones.
- **Still unexplained, and named as such:** *why* the query returns zero for a long goal inside a
  single loaded area. Doc-backed candidates already in this record, NONE tested by G6:

  increasing this limit can allow for path plans on larger nav areas by more entities
  simultaneously" (C:\MAK\...\vrfSim.mtl:383, quoted in PREREG_NAVDATA_G3 sec 0);
  (b) `gamewareQueryTimeBudget` per-frame budget (:389); (c) UG52 66.2.1 p1277 sectorisation -

  C:\MAK - the user's call, not taken here.
