## 0. Verdict in three lines

1. `runner exit: 127` does NOT mean "command not found" and does NOT mean
   PowerShell failed. On this MSYS bash it means the child exited with a
   **high-bit (NTSTATUS-shaped) Windows exit code that MSYS's signal table does
   not recognise**, reported as 127 with no message. Measured, not recalled.
2. Of the codes that produce 127 here, exactly one is **silent by construction**:
   `0xFFFFFFFF` (-1), which is what `TerminateProcess(handle, -1)` writes - i.e.
   .NET `Process.Kill()` / PowerShell `Stop-Process`. Every other 127-producing
   code (`0xC0000409`, `0xC00000FD`, `0xE0434352`) is a CLR fatal error that
   prints to stderr AND raises a WER / Application-Error event. Neither exists.
   **The runner was killed from outside, not crashed.** The killer is not
   identified - no process auditing is enabled on this machine.
3. The "trace: (no samples)" line is a SEPARATE, independent defect and is fully
   explained: `Read-LiveTail` reads the last 256 KB, and at G6's console volume
   256 KB of trace contains **zero** `# t=` summary lines. Measured on the file.

The capture is COMPLETE. Both observers ran to their 1200 s caps and exited
normally. Nothing about the runner's death cost us evidence.

### 1.12 What each status tick cost (supporting, not load-bearing)

Per 5 s poll under `-StopWhenComplete`, the loop calls
`Read-LiveText -Path $PathAppLog` - `StreamReader.ReadToEnd` of the **whole**
app log (RunC2SimScenario.ps1:2750) - and hands the result to
`Get-CompletedTasks`, which does `$AppLogText -split "\r?\n"` over it
(RunnerLib.ps1:97). At ~40 MB that is an ~80 MB UTF-16 string plus a
~500,000-element `String[]`, rebuilt **every 5 seconds**, in a 32-bit host.
Two further whole-file reads are armed behind the all-complete gate
(:2762 the app log again, :2764 the **1 GB trace**), which G6 never reached.

The observed status cadence stretched: ticks at t+44, t+81, t+127 s (gaps 44,
37, 46) against a nominal 30 s. That is 7-16 s of extra work accumulating per
30 s window - consistent with the whole-file read growing. This is a real and
serious defect; it is NOT what killed the runner.

### 3.2 (b) The trace summary must be cheap and correct on a 1 GB file

Two calls to fix; do not just enlarge the window (4 MB still holds only 2
samples and is an 8 MB string every 30 s in a 32-bit host).

**B1 - backward block scan for the status line.** Add beside `Read-LiveTail`
(after RunC2SimScenario.ps1:1090):

```
+# Find the LAST line matching $Prefix by walking BACKWARD in 1 MB blocks, newest
+# first, stopping at the first block that contains one. Peak allocation is one
+# block - not the file, not the whole tail. With member consoles at 4 the summary
+# lines are ~1.6 MB apart, so a fixed 256 KB tail returns nothing (G6, 2026-09-14:
+# "trace: (no samples)" printed against a file holding 162k POS rows).
+function Get-LastLineWithPrefix {
+    param([string]$Path, [string]$Prefix, [int]$BlockBytes = 1048576, [long]$MaxScanBytes = 33554432)
+    if (-not $Path -or -not (Test-Path -LiteralPath $Path)) { return $null }
+    $fs = $null
+    try {
+        $share = [System.IO.FileShare]::ReadWrite -bor [System.IO.FileShare]::Delete
+        $fs = [System.IO.File]::Open($Path, [System.IO.FileMode]::Open, [System.IO.FileAccess]::Read, $share)
+        $end = $fs.Length
+        $scanned = 0L
+        while ($end -gt 0 -and $scanned -lt $MaxScanBytes) {
+            $start = [Math]::Max(0, $end - $BlockBytes)
+            $null  = $fs.Seek($start, [System.IO.SeekOrigin]::Begin)
+            $n     = [int]($end - $start)
+            $buf   = New-Object byte[] $n
+            $read  = $fs.Read($buf, 0, $n)
+            $text  = [System.Text.Encoding]::UTF8.GetString($buf, 0, $read)
+            if ($start -gt 0) { $nl = $text.IndexOf("`n"); if ($nl -ge 0) { $text = $text.Substring($nl + 1) } }
+            $hit = $null
+            foreach ($line in ($text -split "`r?`n")) { if ($line.StartsWith($Prefix)) { $hit = $line } }
+            if ($hit) { return $hit }
+            $scanned += $n
+            $end = $start
+        }
+        return $null
+    } catch { return $null } finally { if ($fs) { $fs.Dispose() } }
+}
```

then at RunC2SimScenario.ps1:2736:

```
-                $sum = Get-TraceSummaryLine -TraceText (Read-LiveTail -Path $PathTrace)
+                $sum = Get-LastLineWithPrefix -Path $PathTrace -Prefix '# t='
```

**B2 - stop re-reading the whole app log every 5 s.** RunC2SimScenario.ps1:2750
is the expensive one (:2762 and :2764 are armed behind the all-complete gate).
Make the app-log read incremental: keep a `$script:AppLogOffset`, open with the
same share mode, `Seek($script:AppLogOffset)`, read only the new bytes, rewind
the offset to the last `\n` in the read so no partial line is parsed, update the
offset, and feed only the NEW text to `Get-CompletedTasks`. Because
`Update-CompletionState` already accumulates across polls (the state hashtable is
owned by the caller, RunnerLib.ps1:105-119), incremental input is semantically
equivalent for `firstSeenUtc`; but `lineCount` is currently "count at this poll"
and must become a running total, so `Update-CompletionState` in RunnerLib.ps1
has to add rather than assign. For :2764 (`Test-ReportEvidence` over the whole
trace), use the same incremental reader on `$PathTrace`, or - simpler - evaluate
it once per 30 s instead of every 5 s.

If B2 is judged too invasive for now, the one-line risk reduction is to raise the
poll interval at RunC2SimScenario.ps1:2727 from 5 s to 15 s and run from a
64-bit host (3.4).

### 3.3 (c) The wrapper: real exit code, and no inherited stdout pipe

**Mechanism (INFERRED, standard Win32):** `Start-External`
(RunC2SimScenario.ps1:876-925) starts every child with
`Start-Process -NoNewWindow -PassThru -RedirectStandardOutput <file>
-RedirectStandardError <file>`. .NET's `Process.Start` with any redirect calls
`CreateProcess` with `bInheritHandles = TRUE`, which duplicates **every**
inheritable handle in the parent into the child - including the handle pwsh
holds as its own stdout, which in G6 was the harness's pipe. `VrfC2SimApp` never
wrote to it, but it held it open, so the harness's read end did not see EOF
until the app was stopped by hand at 10:05Z. That is the nine-hour wait. There is
no `Start-Process` switch that suppresses this.

**Fix - give the runner a FILE for stdout, so there is no pipe in its handle
table to inherit** (`g6_launch.sh` final lines, shown in A1 above):

```
-pwsh ... -File scripts/RunC2SimScenario.ps1 ... -StopWhenComplete
-echo "runner exit: $?"
+"$pwsh64" ... -File scripts/RunC2SimScenario.ps1 ... -StopWhenComplete \
+      > "$SCR\g6_runner.log" 2>&1 < /dev/null
+rc=$?
+echo "runner exit: $rc   (127 = a high-bit Windows exit code, e.g. TerminateProcess(-1) = Stop-Process; see RUNNER_EXIT127.md)"
```

Also add `< /dev/null` to the background sampler subshell (it already has
`> log 2>&1 &`) so it cannot hold stdin either. And per the brief: **never
`| tee` the runner** - a pipe on the runner's stdout recreates exactly this
handle, and `tee` also makes `$?` the exit status of `tee` unless
`${PIPESTATUS[0]}` is read.

### 3.4 (d) The PATH defect that silently undid the 2026-09-07 mitigation

`PREREG_ASSEMBLY_LAYOUT_2026-09-07.md:67` records the mitigation "runner launched
from a 64-bit pwsh (the 32-bit tool host died at 176 MB)". It was a procedure,
not a code change, and it lapsed: the machine PATH is

```
C:\Windows\System32\WindowsPowerShell\v1.0
C:\WINDOWS\System32\WindowsPowerShell\v1.0
C:\Program Files (x86)\PowerShell\7     <-- 32-bit, 7.6.1, WINS
C:\Program Files\PowerShell\7           <-- 64-bit, 7.6.5
```

so bare `pwsh` in any wrapper resolves to the **32-bit** build. Either reorder
the machine PATH, or make it unmissable in the scripts:

```
+# 64-bit pwsh ONLY: bare `pwsh` resolves to C:\Program Files (x86)\PowerShell\7
+# (32-bit, ~2 GB of address space) on this machine, which died at 176 MB on 2026-09-07.
+pwsh64='/c/Program Files/PowerShell/7/pwsh.exe'
+"$pwsh64" -NoProfile -Command '[Environment]::Is64BitProcess' | grep -qi true || { echo "not a 64-bit pwsh"; exit 1; }
```

and, in the runner itself, a hard refusal at startup (beside the other
validations near RunC2SimScenario.ps1:409-410):

```
+if (-not [Environment]::Is64BitProcess) {
+    Say-Fail 'this runner is hosted in a 32-BIT PowerShell. Long runs die of address-space exhaustion in the observation loop (2026-09-07, 176 MB). Relaunch with "C:\Program Files\PowerShell\7\pwsh.exe".'
+    exit 2
+}
```

That last one is the "a rule a checker can enforce should become one" case: it
converts a lapsed procedure into a gate.

- Runner died 00:33:02.6Z, t+127 s into the 900 s window, 346 s after launch.
- The runner contains no exit-127 path; every PowerShell failure mode under
  `-File` exits 1 (or 64) and prints to stderr.
- `pwsh` on PATH is 32-bit 7.6.1; a 64-bit 7.6.5 exists but is later in PATH.
- `ReadToEnd` of the 1 GB trace in this 32-bit pwsh = catchable
  `OutOfMemoryException`, exit 1, loud; and in the runner it is swallowed by
  `catch { return '' }` at RunC2SimScenario.ps1:988.
- bash `$?` = 127 corresponds to raw codes -1, -2, 0xC0000409, 0xC00000FD,
  0xE0434352 (all silent); 0xC0000017 -> 138 "Bus error"; 0xC0000005 -> 139
  "Segmentation fault"; 0xC000013A -> 130.

  this machine (EXCEL.EXE 09-10; VrfC2SimApp.exe 09-13 18:27).
- The 20:41 WER reports attach dumps dated 2026-07-28 and 2026-06-30; last boot
  2026-09-09 01:32; Minidump and LiveKernelReports directories are empty.
- The 20:30:25 `.NET Runtime` / `Category: VrfC2Sim` event is a Warning carrying
  an ordinary BREACH-task log line.
- No `.callstack.log` / `.dmp` in C:\MAK\logs after 2026-09-06 (names/dates only).
- The last 256 KB of the trace contains 0 `# t=` lines, 0 POS rows, 724 CON rows;
  `# t=` lines are ~1.6 MB apart. Stage 7's whole-file read found them.
- Both observers ran to their 1200 s caps, wrote 0-byte stderr, and ListenReports
  wrote its exit epilogue. `observers.stop` was never created.
- RunC2SimScenario.ps1:2822 is already a `finally` teardown covering the window.

**INFERRED:**

- The runner was terminated by `TerminateProcess(handle, -1)` - i.e. a
  `Process.Kill()` / `Stop-Process`. Rests on: 127 = a high-bit code; the three
  other 127-codes all raise WER and print; neither happened.
- The identity of the killer. Not recoverable - no auditing. The

- The ~40 MB app-log size at death (interpolated between two seek-probes).

**UNEXPLAINED (stated, not buried):**

- Nothing was found that names the killing process. If the fix lands without
  identifying it, the same thing can happen on the next run - which is precisely
  why 3.1's backstop must be out-of-process rather than a `finally`.

## 5. Adversarial review

**Strongest competing explanation: a 32-bit-host out-of-memory death**, the same
mechanism documented for 2026-09-07 (PREREG_ASSEMBLY_LAYOUT_2026-09-07.md:500-514)
and still live in the code at RunC2SimScenario.ps1:2750. It was my leading
hypothesis for most of this investigation and it is genuinely present in G6: the
host IS 32-bit, the loop DOES read the whole app log every 5 s, and the status
cadence DID stretch from 30 s to 46 s.

It is refuted on four independent counts, each of which alone would be enough:
(1) reproduced in the same host, a managed OOM exits **1 with a red error
block**, not silently; (2) inside the runner that OOM is swallowed by
`catch { return '' }` at :988, which would have let the loop keep printing;
(3) the OS-level memory death `0xC0000017` maps to bash **138 with "Bus error"**,
not 127; (4) the 2026-09-07 OOM death is recorded as exit **9**. Falsifier that
would reopen it: a reproduction in which a 32-bit pwsh dies with a high-bit exit
code and no stderr while running this loop.

**Second competing explanation: a genuine CLR hard fault** (stack overflow
`0xC00000FD`, unhandled managed exception on a non-pipeline thread `0xE0434352`,
or a fail-fast `0xC0000409`). All three DO map to 127 here. They are rejected
because all three raise a WER / Application Error record, and the control proves
that channel records faults on this machine - including a `.NET Runtime` fault
for VrfC2SimApp.exe nine hours earlier. **Residual risk:** this rests on the
combined log having captured stderr. The supervisor states `g6_launch.log` is
combined stdout+stderr; I could not verify the harness's redirection myself. If
stderr was NOT captured, a "Stack overflow." or "Unhandled exception." line could
have been lost and this hypothesis partially revives - though the missing WER
event still argues against it. **Cheapest falsifier:** on the next run redirect
the runner explicitly (`> file 2>&1`, per 3.3) so stderr capture is not in doubt.

**Third: a bash-level 127** ("command not found", or `wait` on an unknown job).
Refuted: the wrapper runs pwsh in the foreground with no pipeline and no job
control, and pwsh demonstrably ran for 346 s.

**A symptom I did not explain away:** Defender wrote health events at 20:32:41,
21 s before the death. They are Id 1150/1151 (health report), not remediation
(1006/1007/1116/1117), and no remediation event exists in the window - so I do
not believe it is the killer, but the proximity is recorded here rather than
dropped.

**Self-check on my own instrument:** my first kill measurement used a bash
background job plus `wait` and returned 127 for `Stop-Process`. That number was
right for the wrong reason (bash's `wait` returns 127 for an unknown job), so I
re-ran every kill case against a FOREGROUND pwsh - the wrapper's actual shape -
and only those results are used above.
