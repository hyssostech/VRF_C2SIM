## 1. MAJOR - `ShouldDropOldest` does not bound the ring on a frozen clock in the only case that occurs in a run (pause AFTER the ring has filled). The self-test that "proves" it is degenerate.

`src/VrfC2SimApp/StallPolicy.cs:119-121`

    public static bool ShouldDropOldest(double clockNow, double oldestClock, double nextClock,
                                        double windowSeconds)
        => (clockNow - nextClock) >= windowSeconds || nextClock <= oldestClock;

`src/VrfC2SimApp/VrfC2SimService.cs:2672-2673` applies it only to the FRONT PAIR:

    while (ring.Count >= 2 && StallPolicy.ShouldDropOldest(clockNow, ring[0].Clock, ring[1].Clock, window))
        ring.RemoveAt(0);

Rule (b) (`nextClock <= oldestClock`) can only fire when the two OLDEST entries carry the same (or
a decreasing) stamp. A pause that begins after the ring has filled leaves `ring[0]=0, ring[1]=5,
...` strictly increasing, so (b) never fires; and (a) cannot fire either, because `clockNow` has
stopped. Every new sample is appended and nothing is ever pruned, for the whole pause.

Verified offline (`ring_sim.py`, window 240, cadence 5 s, exactly the code above):

    B pause, ring starts empty : final ring=1    max ring=1      <- the case the self-test tests
    C pause AFTER a real run   : final ring=249  max ring=249    <- 400 s of run, then 1000 wall s paused
    D 2-hour pause after a run : final ring=1489 max ring=1489

Each entry is a `Dictionary<string,(double,double)>` of member positions, per unit. The commit
message calls rule (b) "the adversarial-review catch ... a paused sim would add a member-position
sample every StallCheckSeconds forever and prune none of them"; that is still true after the fix,
for every pause except one that starts with an empty ring.

The self-test at `StallPolicy.cs:253-268` seeds the ring at the frozen value from empty
(`ring.Add(simFrozen)` 100 times, all equal), which is the one shape rule (b) collapses. It
therefore passes while the product case fails.

FIX: prune at the BACK, not the front. When the incoming sample's clock is `<=` the last entry's
clock, REPLACE the last entry (`ring[^1] = (clockNow, positions)`) instead of appending - a sample
that carries no new clock information should overwrite its predecessor, which bounds the ring at
one extra entry for any pause of any length and keeps the newest positions. Keep rule (a) as the
front prune. Then extend the self-test to case C above (fill the ring first, THEN freeze).

## 2. MAJOR - the rollback case is broken the same way, and worse: when the window first re-opens after a rollback the code compares a PRE-rollback position sample against a post-rollback one - the exact false stall rule (b) is documented to prevent.

Same lines as finding 1. `StallPolicy.cs:110-115` claims: "a rolled-back scenario would keep
pre-rollback samples that belong to no window. Rule (b) collapses both". It does not, for the same
reason: after `DtVrfRemoteController::rollbackToSnapshot` (`vrfRemoteController.h:605`) the ring is
`[..., 1240, 1245, ..., 1480, 1005]` - the two OLDEST entries are still increasing, so nothing is
dropped and the post-rollback samples pile on the end.

Verified offline (rollback 1480 -> 1000, cadence 5 s):

    i= 295 clock= 1480.0 ring=  49 ring0= 1240.0 span= 240.0 ready=True
    i= 296 clock= 1005.0 ring=  50 ring0= 1240.0 span=-235.0 ready=False   <- rollback
    i= 390 clock= 1475.0 ring= 144 ring0= 1240.0 span= 235.0 ready=False   <- ring 3x its bound
    i= 391 clock= 1480.0 ring= 145 ring0= 1240.0 span= 240.0 ready=TRUE    <- judges post-rollback
                                                                              positions against the
                                                                              sample stamped 1240,
                                                                              recorded BEFORE the
                                                                              rollback
    first ready after rollback: 475 wall s of dormancy, then the cross-discontinuity comparison

A rollback puts the units back where they were at the snapshot; comparing "where they are now"
with "where they were on the abandoned timeline at stamp 1240" is exactly the arithmetic that
manufactures a false TASKABRT.

FIX: on any backwards step (`clockNow < ring[^1].Clock` before the append), drop every entry whose
`Clock > clockNow` and reset `samples.StartClock = clockNow` - i.e. treat a rollback as a new
watch. Self-test it with the sequence above, not with a 2-entry ring (`StallPolicy.cs:250-251` is
the 2-entry version that passes).

## 3. MAJOR - the wall path is NOT behaviourally identical to 51d78a5. The grace anchor moved from `rec.DispatchedUtc` to the watch's first sample, and on the DEFAULT aggregate move path the two are not the same event.

51d78a5 `VrfC2SimService.cs` (parent):

    if ((now - rec.DispatchedUtc).TotalSeconds < _vrf.StallMinSecondsSinceDispatch) continue;

1616614 `VrfC2SimService.cs:2679-2680`:

    if (!StallPolicy.WindowReady(clockNow, oldest.Clock, samples.StartClock,
                                 window, _vrf.StallMinSecondsSinceDispatch)) continue;

`StartClock` is set at the first sample after `ClearStallState` (`:2664`). `ClearStallState` is NOT
called by `MarkDispatched` - by design (`:2179-2185`); on the deferred paths it is called only when
the replacing VR-Forces command is finally issued, in the object-created callback at `:2418`. But
`MarkDispatched` DOES write a new in-flight record with a destination at `:2049` (R11 plan-move)
and `:2146` (the DEFAULT `CreateRoute` + `MoveAlongRoute` path for every aggregate move). Between
those two points the unit has a NEW in-flight move task and its OLD ring and OLD `StartClock`.

- 51d78a5 re-armed 60 s of grace at that moment (the anchor was the record's own `DispatchedUtc`),
  so no report could be emitted for the new task inside that window.
- 1616614 has no gate there at all: the stale ring can satisfy `WindowReady` on the same tick the
  new task is recorded, and the resulting TASKABRT is attributed to the NEW task uuid
  (`rec.TaskUuid`, `:2691`) while being computed entirely from the previous task's samples.

Exposure is normally the route-creation round trip (short), but it is UNBOUNDED in exactly the
failure this watchdog exists for: if the route-created callback never arrives - the observed
"tasked and then silently froze; route name 44 chars, 0 offset routes" mode cited in this file at
`:2398-2401` - `ClearStallState` never runs, and the old ring/anchor persist for the rest of the
run.

This also refutes, in the general case, the report's claim that the redefinition is inert (see the
PASSED list: it IS inert once the anchors coincide; these paths are where they do not).

FIX: clear the stall SAMPLES in `MarkDispatched` whenever `dest` is non-null (the arrival-swallow
argument for deferring `ClearStallState` is about `_arrivalReported`, a different map; the stall
window has no reason to survive a dispatch). Equivalently, keep the old `rec.DispatchedUtc` wall
grace as an additional AND - which also buys back finding 4.

## 4. MAJOR - no wall-time floor survives anywhere. A forward clock step >= the window opens the gate after TWO samples, and the measured span can exceed the configured window without bound. "The cadence is a sampling rate, not a measurement" is false.

`VrfC2SimService.cs:2605-2607` keeps the cadence on wall time and the comment at `:2609-2611`
argues that this is harmless. It is not: with the window on the sim clock, the cadence sets both
the ring resolution (`window / (cadence x ratio)` samples) and the minimum WALL exposure before a
verdict. Nothing else bounds either, because the only wall-side floor in the old code was the
grace that finding 3 removed.

Verified offline (cadence 5 s, window 240):

    F 60x ratio: first ready at SAMPLE 2, measured span 300 sim s (25 % over the configured 240),
                 10 wall seconds after the watch opened, ring = 2

At G5's measured 6.21x it is 9 samples / ~40 wall s (the commit celebrates this as "38.6 wall s").
At the COA-STP1 ratio of 0.27x it goes the other way: ~178 entries per unit (vs a fixed ~49
before) and ~889 wall s to fill - a 3.6x growth in the per-unit buffer the old code bounded.

Two consequences, both new:

 (a) a verdict can be reached on 2 position reads; a member whose reflection has not updated in
     that interval contributes 0 m and cannot be distinguished from a frozen one;
 (b) the effective window is `max(240, cadence x ratio)` sim seconds, so the abort point drifts
     with load - which is the same thing the commit is trying to fix, in the other axis.

FIX: require a minimum ring depth before judging (>= 4, say), or keep a WALL floor equal to the old
grace, or scale `StallCheckSeconds` by the reported ratio (`DtBackend::simTimeToRealTimeRatio()`,
`vrfutil/backend.h:263`, is reachable through the same back-end listener and would give it).

## 9. MINOR - a STALE (not paused) sim clock disables the watchdog silently, and the `-1` gate does not catch it.

`VrfFacade.cpp:600-612` gates on `backends().count() > 0`. A back end that stops responding is
DEACTIVATED, not removed: `vrfBackendListener.h:161-163` "Goes through the status object list and
deactivates any status objects which have not responded within the timeout interval", while
`:154-155` documents `remove()` as "Normally, this should not need to get called!". So `count()`
stays > 0 and `simTime()` keeps returning the last cached value. The watchdog then sees a frozen
clock, treats it as a paused scenario, and reports nothing - for the rest of the run, with no
diagnostic. The whole point of C16 is to catch a silence; this adds a new silence in front of it.
FIX: if the sim clock has not advanced for N wall seconds while move tasks are in flight, log a
warning (and consider falling back to wall until it moves again).

## 10. NOTE - answers to the brief's item 2 (`count() > 0` while `simTime()` is still 0.0).

Yes, that state exists: `backends()` holds every back end whose STATUS message has been heard
(`vrfBackendListener.h:89-90`), and the status message's sim time defaults to 0.0
(`vrfmsgs/ifStatus.h:85-87` "simulation time ... in seconds (defaults to 0.0)"), so a back end that
is discovered but has no scenario loaded reads 0.0. A window opened at 0.0 does NOT misbehave:
`StartClock = 0.0`, the clock does not advance, the ring collapses to a single entry (this IS the
empty-ring case rule (b) handles), and `WindowReady` stays shut until the scenario runs. The
failure mode is dormancy, not a false abort. The residual risk is finding 4's: if a 0.0 reading is
ever followed by a jump of >= 240 (adopting an already-running back end after reading 0.0 from a
not-yet-loaded one), the gate opens on two samples.

## 12. NOTE - wall-second precision changed (immaterial).

`VrfC2SimService.cs:2628-2629` derives wall seconds as `now.Ticks / (double)TimeSpan.TicksPerSecond`
instead of differencing `DateTime`s. At the current epoch (~6.4e10 s) a double's ULP is 2^-16 s =
~15 microseconds; the old path was exact tick arithmetic. Against a 240 s window with a >= 1 s
enforced cadence this cannot flip a comparison in practice.
