# STP-872 SCOPE - obstacle objects from C2SIM graphics so BREACH has a target (PAPER ONLY)

STATUS: scope for the STP-1097 supervisor (2026-10-15). No code, no native build, no live run until it is approved.
Ticket ask: create VR-Forces obstacle objects (minefields, antitank ditches, wire, abatis - STP's obstacle masks) from
C2SIM TacticalGraphics, and resolve a BREACH task's AffectedEntity (the obstacle graphic's uuid, STP-865) to that object.

## What the vendor offers (VR-Forces 5.2 Users Guide; text extract docs/vendor/mak-5.2/txt)

- Combat engineering objects (CEOs) are aggregate-level objects shown as tactical graphics. They are created from the
  Create Object Palette or by a unit's construct task. They change MOBILITY: a unit that meets an obstructing CEO STOPS
  and asks the operator what to do, by console question (UG52 27.2, p533-534). That is a demo-visible behaviour change.
- "Breach Obstacles" (UG52 35.3.1, p719) is an AGGREGATE-level combat-engineering task for an ENGINEERING unit. Its
  parameter is a two-point BREACH LINE, not a target object, and success depends on the unit's breaching system.
- Entity-level DtBreachTask takes a breach TARGET (VrfFacade::Breach / setBreachTarget, already in the facade).
  RL-20260926-01 notes there is no breach controller in EntityLevel.

## What this means for the interface

1. CREATE (new). There is no facade call for an areal or linear CEO object today: CreateControlArea creates a tactical
   graphic, not a CEO. This needs a NATIVE facade + bridge addition (create an object of a CEO object type with a
   perimeter or line), a new pin, and a deploy. Before that, a doc + live-probe step (1 run) to find the CEO object
   types in the AggregateTacticalLevel model set and confirm a remote controller can create them.
2. BREACH (behaviour change). On the demo's aggregate model set the vendor breach is "Breach Obstacles" with a line:
   - the task's obstacle graphic gives the line (its geometry), so no object target is strictly needed for the
     aggregate path;
   - the performer must be an ENGINEERING unit. The Iron Storm containers' compositions carry no engineer subordinate,
     so a BREACH by them stays not-simulated unless the composition table gains engineers (data change, separate
     ticket) or the breach is given to an engineer member.
   - RL-20260926-01 rules BREACH = advance + "breach not simulated" observation, no DtBreachTask. Changing that is an
     OWNER RULING.
3. RISK. Creating CEOs puts real obstacles into the routes. Units stop at them and ask questions (unattended runs would
   wait), and the planner re-plans around them - near the class of re-plan the STP-1163 hang lives in. The demo must
   not get this; it belongs behind a setting that is OFF by default.
